# 后续更新注意事项与踩坑记录

供维护者和参与开发的工具在修改、升级、发布前阅读。操作步骤见 [发布指南](PUBLISHING.md)，用户说明见 [项目首页](../README.md)。本文根据 0.8.0 首次公开发行和现有实现整理，初始记录日期为 2026-11-06；以后遇到新问题，在本页补充原因、解决办法和验证方法。

## 先判断这次是不是发版

| 修改内容 | 应做的事 |
| --- | --- |
| 仅补 README、维护说明或其他文档 | 可以提交到 `main`，无需为了文档单独提高插件版本。不要覆盖已发布版本的源码 ZIP；它对应当时的标签，不是不断变化的 `main`。 |
| 修改会进入 XPI 的代码、界面、图标、清单或其他文件 | 分发给用户前提高版本、重新构建和验收，按新标签发布。 |
| 修改构建、更新或发布脚本 | 验证相关回归；若改变候选资产，重新构建并核对。已经公开的发行文件仍然保留原样。 |
| 发现已公开版本有缺陷 | 在更高版本修复，写明影响和处理方法；不要移动旧标签或以同名文件静默替换旧包。 |

`main` 有新提交不代表用户已更新；创建标签不代表正式发布；正式发布也不代表插件市场已收录。

## 身份、版本和更新地址

- **保留插件 ID `fulltext-assistant@local.invalid`。** 这是已有安装的身份标识，不能因为看起来像占位地址就改名，否则会被视为另一个插件。它与实际网络更新地址是两回事。
- 偏好前缀 `extensions.fulltext-assistant.` 和数据目录 `fulltext-assistant` 也属于升级兼容约定。界面版本从安装器传入，不另造一套手写版本常量。
- 新版本同时修改 `manifest.json`、`package.json`、`package-lock.json` 顶层和 `packages[""].version`。仅执行 `npm version` 不能代替核对 Zotero 清单。当前构建脚本要求三段稳定版本号，不支持直接填入 `-beta`；需要测试频道时应先设计相应构建和更新规则。
- 保留公开的 `releases/latest/download/updates.json` 更新入口；清单内的 `update_link` 应指向具体版本的 XPI。不要填入本机路径、临时地址或需要令牌才能访问的私有资源。
- 改 Zotero 兼容范围时，同时检查 `manifest.json` 和 `build.py` 中的版本约束，以及用户文档与原生验收结果。0.8.0 的原生实测环境为 Windows / Zotero 10.0.7，不能把 Linux CI 成功写成 Linux Zotero 已验证。
- 原始 0.7.x 使用旧更新地址，需要手动安装一次 0.8.0 或之后的版本。用修改过更新地址的旧版测试包验证成功，不等于原始旧包可以自动更新。

参考实现：[构建配置与更新清单](../build.py)、[插件清单](../manifest.json)。

## 数据与任务升级：不要把加载失败当成空文库

任务包含跨批次历史、附件关联、科研通求助关联、支出和待收尾信息。改字段时检查序列化、反序列化、默认值、状态转换和界面筛选，不能只改新建任务的分支。

1. 先用去隐私的旧版数据构造升级样本，覆盖未完成、已获取、待人工核对和入库后尚未采纳/已读的任务。不要把用户真实任务、PDF 或凭据提交到测试目录。
2. 当前队列格式的 `SCHEMA_VERSION` 为 `1`，解析器会拒绝不支持的格式，清理函数也会过滤未知状态或不合规条目。新增状态要同步维护 `STATES`、转换和恢复逻辑，并测试旧数据“读入—保存—再读入”不丢任务。若升级格式，先实现旧格式迁移与失败恢复，再提高编号；加载失败时保留原文件，不要自动用空队列覆盖。
3. 升级后核对任务 ID、当前批次、历史排序、原附件、求助关联、已确认的积分金额和收尾状态。新批次只能更新当前批次视图，不能清除跨批次未完成与完成历史。
4. 改存储位置、文件名、凭据键或会话格式时，提供读取旧数据的路径。不要通过清空配置、任务文件或登录数据来让测试通过。
5. 数据备份与恢复需考虑 Zotero 正在写入的情况。在隔离配置验证，不能把运行中的数据库文件直接覆盖回正式文库。降级也可能无法读取新格式，不能只换回旧 XPI 就宣称完整回滚。

参考：[任务模型](../src/task-model.js)、[加载、保存与任务执行](../src/app.js)、[账号凭据](../src/credentials.js)、[机构会话](../src/publisher-session.js)。

重启时，正在提交的 `submitting` 任务必须转为 `submission_unknown`，不能当作普通下载任务重新提交。保留求助前先持久化 claim、采纳前先持久化 `needsReconcile` 的顺序；这两步用于防止响应丢失后重复消费。换账号或退出后，旧异步响应不能恢复上一账号的消息、余额或会话。

**0.9.0 已修复启动失败风险（2026-11-09）：** 只有任务队列成功读取（或确认原文件不存在）后才允许保存。损坏 JSON、不支持的 schema 和读取异常均有回归，调用停用流程后原任务文件字节保持不变。不要移除 `queueLoaded` 保护。PDF 已提交但暂停/关闭同时发生时，必须先记录真实的附件 ID 与来源；关闭还要等主任务的提交收尾，防止旧实例在新版加载后再写旧快照。


## 按改动选择需要回归的行为

| 改动范围 | 至少核对这些场景 |
| --- | --- |
| 批量和队列 | 已有有效本地全文直接跳过；处理中再添加一批会追加而不覆盖；重叠选中同一条目不会重复求助或导入；取消、暂停和重启后状态可解释。 |
| 任务面板 | 进行中、需网页登录、待兜底、已获取只看当前批次；未完成、全部历史跨批次保留；PDF 已入库但采纳/已读未结束仍有处理入口；标题和 DOI 复制反馈正常。 |
| PDF 身份核对 | 综合 DOI、标题与版面证据判定；可靠 DOI/标题冲突不得自动通过；参考文献 DOI、页眉、断行、连字符、超链接和扫描件分别覆盖。证据不足进入人工核对，低相关文件不要堆入候选。DOI 前缀或格式合法不等于就是目标论文。 |
| 浏览器下载 | 自定义目录、默认目录、尚未写完的文件、修改时间、多个同时等待任务、手动重查和选文件路径。监控当前只检查配置目录的直接文件，重启不恢复原监控计时；不要在文案里宣称递归扫描或持续后台监控。 |
| 科研通与积分 | 提交超时先核查是否已发布；响应不明不能再次发布或再次采纳；正确文件保存后才采纳具体应助文件；仅标记对应上传通知已读；本地手选文件不能未经来源核验就改成科研通渠道。 |
| 科研通价格与统计 | 排队任务保留启动时授权金额；按钮按设置显示；最低悬赏必须有网站依据；余额不足、金额不明、旧任务金额缺失分别处理；统计不把未知金额或未采纳任务当成已支出。 |
| 登录与生命周期 | 关闭并重启隔离 Zotero 验证会话恢复、过期、账号切换和退出登录；卸载/更新时旧定时器、观察器和任务停止，重新加载后不会重复轮询。不要把文件存在或仅重建应用对象当作跨进程登录已验证。 |
| 设置与语言 | 简体、繁体、英文都能显示新字段、状态和错误；长文本不溢出，默认值与实际执行一致，旧用户缺少新设置时有合理默认。新增联网或数据保存行为同步修改隐私说明。 |

相关测试位于 [tests](../tests)，设置页回归为 [ui/prefs.test.cjs](../ui/prefs.test.cjs)。按变更补充能复现问题的测试，不用每次重复无关的真实网站操作。普通批量获取不能因为重构而默认变成付积分求助；签到当前由用户在官网操作，状态查询与自动签到是不同功能。

## 本次发布实际遇到的坑

### 更新 Release 时省略标签，草稿可能失去关联

0.8.0 草稿曾在只更新 `name`、`body` 后出现 `untagged-…`。实际 Git tag 仍存在，但 Release 已不再按预期标签被找到。不要因为找不到草稿就立刻创建第二个。

- REST PATCH 更新发行说明或发布状态时，显式带上已核验的 `tag_name`；发布时同时带上已核验提交的 `target_commitish`。使用 GitHub CLI 时也确认操作的是预期标签。
- 写入前核对 Release 数字 ID、标签和 Git 引用；写入后确认同一个 Release ID、标签和目标提交关系没有改变。稳定版还需检查 `draft: false`、`prerelease: false` 与 latest。
- 恢复丢失关联时，只修正确认过的那个草稿，并保留资产；不要移动已公开标签或批量删除发行记录。
- 这项行为已被 [发布脚本](../scripts/release.py) 和 [请求体/身份回归](../tests/test_release.py) 覆盖。后续重构不能只模拟 `publish()` 成功，还要检查真正发出的 PATCH 字段。

GitHub CLI 也显式保留标签，参考 [v2.96.0 的 release edit 实现](https://github.com/cli/cli/blob/v2.96.0/pkg/cmd/release/edit/edit.go)。

### 按标签查询返回 404，不一定没有草稿

已认证的按标签接口在此次发布中未能返回既有草稿。当前脚本先分页列出发行记录，找出唯一匹配标签，再按数字 ID 读回确认。遇到 404 先检查身份权限、列表和已有草稿，不要盲目重复创建；同标签出现多条记录应停下来排查。

### 候选变了，自动工作流会拒绝覆盖旧资产

推送标签触发的准备流程默认不覆盖不同内容的文件。这是保护措施：如果未发布候选确需调整，先核对新提交、测试和资产，再明确选择 **Prepare release candidate → replace_draft_assets**，或使用 `--replace-draft-assets`。不要靠反复重跑同一个未授权覆盖的流程解决。

更稳妥的顺序是先完成审查和 CI，再定标签；非必要不重指向未发布标签。已发布标签永远不按候选处理。准备与发布工作流共用并发组，保留这项限制，避免两个任务同时修改同一发行。

### 相同版本号不代表相同字节

固定排序、ZIP 元数据、LF 换行和 ZIP_STORED 是当前跨平台可复现构建的一部分。更改压缩方式、换行或归档工具后，要重新比较本机和 Actions 构建结果。

文档变化通常只改变源码 ZIP；业务代码变化会改变 XPI。发布前应分别记录 XPI 哈希与源码/清单哈希，核对五份资产的完整集合。公开后即使只想补文档，也不要替换旧源码包；可以提交到 `main`，或补充 Release 说明中的后续验证结果。

### 文件扩展名和截图内容都要检查

首次准备截图时，实际图像编码曾是 JPEG、文件名却是 `.png`；已改为 `.jpg`。后续截图检查实际编码、引用路径与元数据，并使用空白或合成演示文库，避免把账号、文献、个人目录和会话信息公开。构建允许列表也不能替代内容检查：即使文件被 `.gitignore` 忽略，只要归档扫描会选中它，也必须移出构建输入。

## 一次新版本的发布检查表

- [ ] 确认版本、插件 ID、兼容范围、更新地址及新功能文案一致；功能或数据格式变更已有对应升级验证。
- [ ] 运行 `npm ci --ignore-scripts --no-audit --no-fund`、`npm test`、`python build.py --output dist`、`python scripts/release.py verify-local --directory dist`。
- [ ] 使用实际候选 XPI 在隔离 Zotero 验证相关流程，记录版本、提交、文件哈希和测试范围。模拟接口、真实下载、人工操作和真实付积分操作分别记载。
- [ ] 检查工作树及归档输入，提交全部批准的源码；确认精确提交的 CI 通过，再创建对应标签。
- [ ] 等待候选草稿准备成功，检查五份资产、发行说明与已验收 XPI 哈希一致；不使用“同名旧包”替代实际验收。
- [ ] 执行独立的 **Publish reviewed stable release**，填入目标标签和已验收的完整 XPI SHA-256；读回稳定版和 latest 状态。
- [ ] 匿名下载五份资产核对内容，验证 `latest/download/updates.json`；用已配置当前公开更新入口的较低版本隔离安装执行 Zotero 原生更新发现与安装，再核对启用状态和升级后的任务、设置及附件关联。
- [ ] 在 Release 说明记录实际完成的结果；测试数量属于对应版本，不沿用旧版本数字充当新验收。
- [ ] 结束临时测试进程，核对正式文库未被测试替换；保留必要的本地诊断材料，公开材料去除个人数据。

如果公开更新暂时未生效，依次核查 Release 是否稳定且为 latest、更新清单能否匿名取得、插件 ID/版本/兼容范围/链接/哈希是否匹配，再检查网络、缓存和 Zotero 的更新结果。不要先清空用户任务或登录状态。发布后发现问题通常需要更高版本修复；改变 latest 或要求降级前应评估已经升级用户的数据兼容。

## 0.9.0 全文来源与原生更新维护补充

- API 元数据命中、候选链接存在、HTTP 200、PDF 格式有效和身份匹配是不同步骤。只有附件提交后才能记“已获取”；遇到冲突拒绝导入，证据不足保留一个 hash 绑定候选，重启仍能核对。不可为了让真实下载测试通过跳过身份门槛。
- DOI 可能在首页排版靠后的位置，题名也可能很短。修识别要用真实、可公开论文的局部版面结构构造回归，同时覆盖参考文献、页眉、正文引用及冲突 DOI；不能把“包含目标 DOI”当成匹配。
- PMC 旧 `oa.fcgi` / OA Web Service 已在 2026-08-25 停用。本版使用当前 Article Datasets 的 JSON `pdf_url`，不推测文件地址。接口有返回不代表旧文档仍有效，升级前重新查官方说明。
- OpenAlex 的缓存可用性来自 `has_content.pdf` / `content_urls.pdf`，不能用 `has_fulltext` 代替。下载 key 通过限定端点的认证头发送，不放进 URL。没有开启内容额度就不能下载缓存，即使已经填 key。
- 本机额度按 UTC 日期与 key 哈希预留，先落盘再下载，失败也计次。持久化失败或损坏需拒绝缓存下载；不可把计数文件重置为空来“修复”。本机计数不是提供方余额，不能承诺不会消费付费额度。
- CORE 与 Semantic Scholar 可先尝试匿名请求；401/403/429 不能直接推断成“必须购买”。测试说明分别记录无 key、带 key、真实 PDF、外链候选与访问限制。
- 自定义来源不继承科研通/机构会话。API 和自定义下载必须保留 `anon:true`、`followRedirects:false`，逐跳核验并在 origin、路径或 query 改变时去掉认证头。凭据不可进入候选、进度、错误正文或历史。DNS 预检不等于固定实际连接 IP，不宣传完全消除 DNS rebinding。
- 来源配置保存前严格校验模板和额度；读取旧设置可安全回退，但不能在用户保存时悄悄丢掉无效输入并宣称成功。定时快照及语言切换不能覆盖未保存草稿，API key 留空保留，明确清除才删除。
- DOI 模板占位符必须位于路径或查询参数；只有 `#{doi}` 时浏览器不会把 DOI 发给服务器，必须拒绝保存。诊断 `metadata_only` 只说明 API 的作用，不等于已经找到下载地址；版本偏好当前是筛选规则，文案不能承诺出版版排序。
- 更新控制器使用安装实例的原生 AddonManager；手动检查只发现、用户安装才启动，自动开关同步 `applyBackgroundUpdates`。不要引入任意更新 URL 或自己的 XPI 安装器绕过兼容/哈希核验。原生 API 可能以 error 状态而非异常返回，UI 必须检查。
- 更新替换插件时 `destroy()` 只拆自己的监听器和计时器，不取消已在替换自身的原生安装。原生安装阶段不能照下载阶段强行取消；超时需说明状态未知并避免重复安装。
- 公布 0.9.0 后用真实、未篡改的 0.8.0 XPI 验证原生发现与安装。候选 0.9.0 检查当前公开 0.8.0 只证明不会降级，不是 0.8→0.9 升级成功证据。验证后核对任务、原附件关联、设置与登录状态，记录准确候选哈希。
